# Lux 功能补齐分析

调研日期：2026-11-12。目标是 Windows 轻量英雄联盟助手，沿用 MyGo + Go + Vue，优先保持滚动、鼠标响应与低后台开销。

## 结论与本轮落地

Lux 已有自动连接、战绩查询、十人分析、选人侧栏、英雄强度、Buff/Debuff、自动选禁、回放、AI 时间线和更新机制。当前更需要把“看到信息 → 判断 → 查看依据 → 返回原处”连起来，而非继续增加入口。

本轮实现三个明确需求：

1. 单局与战绩记录的主文字使用召唤师名字，英雄保留头像；英雄选择器、常用英雄统计仍显示英雄名，便于选择。
2. 对局与十人面板显示“遇到过”徽标；悬浮或键盘聚焦查看之前的队友/对手记录，点击打开该场详情，保留原页面。
3. 展示“疑似预组队”及证据对局。只统计近 30 天、本局之前、已读取的有效匹配，至少 3 场真实同队；相同对局跨玩家来源去重，重开与自定义不计入。

交手记录本轮基于当前账号已读取的战绩，默认 50 场，可在分析设置提高到 200 场。它不是跨设备或无限期的社交档案。完整长期记录及手工标签作为下一批独立模块，不把已读样本之外的情况显示成“从未遇到”。

### 补充核查：AKL 的好抓、通天代与组队标签

2026-11-12 根据用户指出的具体功能，继续追踪数据计算、阈值、标签和翻译文案。前述差距表遗漏了这些已经存在的 AKL 能力；它们有明确源码规则，可以迁入 Lux，并非需要从零设计的模型。以下描述的是当前本地参考源码，不等同于这些标签已在 Lux 实现。

**好抓 / 难抓。** `src/shared/data-adapter/analysis/player/single/early-deaths.ts` 统计召唤师峡谷、经典模式、匹配对局中，玩家在前 15 分钟（代码包含恰好 15:00）被敌方打野击杀或助攻击杀的次数。历史该场玩家为打野时不参与；打野识别优先使用位置，敌方位置缺失时回退惩戒。`aggregate/details.ts` 只对非空有效值求场均，无法识别敌方打野的比赛不以零计入。

标签阈值位于 `src/renderer-shared/components/ongoing-game-panel/widgets/player-info-card/player-card-tags/tags/basic.tsx` 的 `getEasyGankTag`：

| 前 15 分钟敌方打野参与击杀的场均次数 x | AKL 标签 |
| --- | --- |
| x < 1 | 难抓 |
| 1 ≤ x < 1.5 | 可抓 |
| 1.5 ≤ x ≤ 2 | 好抓 |
| x > 2 | 非常好抓 |

当前玩家是打野或无可用统计时不显示标签。该函数没有独立的最低样本门槛；悬浮文案使用 `detailsCount`，但实际平均数仅采用非空的早期死亡值，混合打野与非打野等样本时二者可能不同。Lux 迁入时应保存真实参与计算的样本数，缺失时间线不算零；建议少于 5 场仅展示次数与“样本较少”，5 场是 Lux 的产品建议，不是 AKL 现有阈值。这项统计是已发生的打野参与击杀次数，不是所有抓人尝试的成功率。

**优异 / 通天代。** `aggregate/akari.ts`、`scoring.ts` 与 `constants.ts` 计算近期聚合的 Akari Score，`tags/great-performance.tsx` 将其展示成标签。各项上限为 KDA 1、胜率 1、伤害 3、承伤 2、补刀 2、经济 2、参团 2、视野 2，共 15 分。KDA 使用截断的平方根曲线；胜率在 50%–100% 映射为 0–1 分；补刀在每分钟 5–10 个映射为 0–2 分；参团率在 30%–100% 映射为 0–2 分。伤害、承伤、经济与视野相对同队平均贡献计算后，逐场评分再求平均；经济相对平均贡献 1.5 倍达到该项满分，其余三项为 2 倍。

- 聚合分 ≥ 6.5 且有效场数 ≥ 5：优异。
- 聚合分 ≥ 8 且有效场数 ≥ 8：通天代，展示优先于优异。

该评分函数不读取段位差、账号等级或操作者身份；“通天代”是达到上述表现阈值的文案。另有独立的 `tags/suspicious-flash-position.tsx`：样本中闪现放 D 与放 F 均出现过，就显示“闪现异位”并展示两侧次数/占比。它没有时间顺序突变、最低次数或身份验证规则，不应直接升级成已确认代练结论。

**谁与谁开黑。** AKL 合并两条来源，而不只依赖历史重复同队：`ongoing-game/computed-state.ts` 从当前 gameflow 双方成员的非零 `teamParticipantId` 分组；`additional-info-controller.ts` 在对局进行中、远程配置允许且请求可用时，经 SGP GSM 补充分组、英雄、位置和召唤师技能。`state.ts` 的 `mergedPremadeTeamMap` 将这些分组与历史推断组合，过滤跨当前队伍的组，渲染成小队 A/B 等颜色和标签。

历史推断由 `analysis-controller.ts` 和 `team-up-calc.ts` 完成，当前设置默认门槛 5 场（工具函数自身默认值为 3），还会移除子集并合并重叠集合。Lux 0.2.14 仅落地历史共同同队证据，缺少客户端分组通路及逐玩家 A/B 标识；后续应保留“客户端分组”和“历史推断”的不同来源，直接分组不强制凑满历史门槛，字段为空时不把所有人归成一个组。竞技场的实际小队还需区别于峡谷预组队。

本次追踪到的直接分组通路面向当前对局；常规历史比赛的 `toParticipants` 和单局 `TeamTable` 中没有发现通用的原房间队长字段。查询历史某场时可提供组队推断，但应仅使用该局发生之前的证据；以后若在当前对局捕获了真实分组，可以按游戏和区服保留来源用于回看。房间成员的 `isLeader` 是另一项当前房间信息，不能由小队 A/B 编号反推历史建队者。

## 产品模型与模块划分

### 1. 玩家档案，而非散落的小开关

统一模型建议包含 `AccountScope { selfPUUID, region, platform }`、`PlayerIdentity { puuid, riotId, icon, level }`、`PlayerNote`、`EncounterRecord`、`PinnedPlayer`。展示页继续使用现有 `Profile`，本地备注与交手资料通过小型独立接口补充，不把长期档案不断塞进周期快照。

交手记录至少保留比赛 ID、服务器、时间、当时双方队伍关系、来源、当时 Riot ID 和可查看状态。历史改名不能让记录断开；切账号不会把上一人的主观备注套给新账号。只有在记录范围超出当前历史窗口时，才需要明确的保留天数与容量上限。

### 2. 选人决策卡，而非多个互不关联的榜单

选人后以当前英雄为中心显示四块：本人可用皮肤、当前模式调整、个人近期样本、符文出装。峡谷另提供分路和对位；大乱斗显示个人 2–3 选项及替补池，推荐只在合法可选范围内。

任何方案至少关联模式、位置、版本、服务器、分段、样本数、来源时间。应用符文或技能前，后端重新核对当前英雄、选人会话和可写状态；用户改变选择后，过期请求不能写入新的英雄配置。

### 3. 复盘页由证据组织

每条结论可以展开“发生了什么、与谁比较、从哪条数据得出”，并跳转时间线对应分钟。没有位置、视野或技能使用数据时，不推断“应该看到”或“技能空了”。先把已有金钱、补刀、经验、击杀事件和目标争夺讲清楚，再接入更细指标。

## 性能与验证约束

- 账号或比赛变化触发分析，鼠标移动、悬浮和滚动不触发历史抓取；徽标读取缓存计算结果。
- 交手索引只针对当前本人已读历史建立；预组队共享去重比赛集合。五人队伍最多 31 个成员子集，规模由当前阵容限制。
- 浮层默认展示最近 8 条证据并独立滚动，长战绩列表继续虚拟化；说明不常驻挤占十人表格。
- 不把组合统计当成本局胜率；不把有共同队友的间接链条当成全员共同组队。
- 关键验证包括改名/同名、双来源重复比赛、同队/对手、历史回看不能读取未来证据、账号隔离、空样本、失败重试、浮层键盘操作与返回原处。
- 符文、录屏、实时面板及自动化新增动作分别设置独立生命周期和测试；不因增加展示功能引入高频全量快照。

## 推荐推进顺序

第一批完成本轮名称、交手证据和历史预组队，并替换桌面程序、发布单 EXE。根据补充核查，下一批先补客户端分组与逐玩家小队标识、好抓/难抓统计和可解释表现标签；其数据层同时补齐技能槽位与视野等字段。随后推进玩家档案（备注、收藏、长期交手）与单局装备/符文详情，形成个人长期价值。再接入版本化符文出装和按需应用，深化 AI 证据定位。实时悬浮窗与录屏在前述功能稳定、后台开销有实测预算后独立推进。
