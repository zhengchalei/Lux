# Lux 产品梳理

2026-11-10。基于当前界面、实际功能和代码行为梳理。

Lux 的核心价值应当是：选人时知道阵容缺什么、当前英雄能做什么；开局前快速看懂双方状态；赛后找到值得改进的表现。Windows 原生、小体积、低内存和交互流畅，是整个产品的使用前提。

目前已经具备战绩、选人、强度、查询和自动选禁，但信息组织仍偏向逐项展示功能。接下来的重点应该是让用户更快完成判断，并且看得懂每个结论用了哪些数据。

**本轮数据架构与分析改造（2026-11-10）**

- 战绩改为 SGP 优先、LCU 回退，按准确队列分页；显示来源、目标、读取、扫描与有效场数。真实十人均取得同队列 50 场，本人查询取得 200 场。
- 客户端使用 HTTP 初始快照与 WebSocket 事件同步；玩家、公共数据与禁选各自执行。并发有上限，主动查询保留名额，旧账号和旧房间的任务会取消。
- 首批记录先展示，扩量与完整比赛补全继续执行。单人失败不影响其他玩家，扩量失败保留已读样本，进度与最终完成分开。
- 查询页增加准确队列、英雄近期样本及伤害 / 承伤 / 经济占比；每项占比带独立可用场数。统计在后台准备，UI 通过消息唤醒。
- 十人各 50 场的持续重绘诊断 P95 为 5.60 ms，查询 50 场为 2.53 ms。实际滚动、鼠标与切页输入延迟尚未完成验收。
- 模块与当前实现见 `architecture.md`；下面保留先前产品观察及后续工作区建议，不代表所有规划都已实现。

**此前已落实**

- 移除选人示例入口、预设阵容、手动切换示例模式及相关状态。
- 移除随程序分发的个人战绩、捕获时间及预置对位结果。启动后等待客户端返回当前账号的数据。
- 选人模式由真实房间决定；未连接、未选人、暂无战绩时展示对应状态。
- 保留真实公共英雄目录、头像、模式强度和调整缓存，以及来源和版本说明。
- 保留主动加载真实历史对局的“复盘最近一局”。这是正式功能。

**已完成的第一批 P0（2026-11-10）**

- 对战助手支持当前范围与全部模式；本轮进一步改为按当前准确队列获取。查询条件变化会重新取样，资料内部的模式与英雄汇总在后台预计算。
- 同一局刷新保留已有资料，逐人显示更新中、成功或失败；失败可单独重试，保留资料仍使用原来的读取时间。
- 顶栏显示当前账号与客户端返回的区域 / 区服代码；检测到账号变更后清理个人视图与缓存并关闭自动选禁。未取得区服细节时不猜测大区名称。
- 十人双列布局保留，新增统一进度与卡片读取时间。模式设置兼容已有分析场数配置。
- 真实历史读取中，一名玩家返回 50 场，全部模式有效 47 场、当前海克斯模式有效 35 场；另一名玩家分别为 49 / 49 场。不是将读取总数当作同模式样本。

下方清单保留整体规划。其中同模式统计、刷新状态和账号 / 区服标识已完成第一批；流畅度的完整验收、页面合并及其他条目继续按建议评估。

**自动同步与界面整理（2026-11-10）**

- 移除顶部“连接客户端”和“更新强度数据”。客户端启动即自动发现，断线后重新发现认证，权限等原因会在状态区解释。
- 强度数据在启动时联网获取，完整更新后每 6 小时检查，失败或部分更新时 5 分钟后自动重试，期间保留带来源的缓存。
- 公共请求迁到独立线程，联网等待不阻塞客户端连接和阵容轮询；对位回复按请求代次校验，定期目录更新保留已有对位查询。
- 导航改为深蓝侧栏，主题入口移至侧栏底部；顶部展示页面与当前账号，底部展示操作结果与自动更新状态。
- 自动选禁总开关集中在本页的运行状态卡，六项行为设置使用独立开关，候选顺序与英雄库采用分层卡片。启动默认关闭的规则保持不变。
- 对战助手保留双列五行、核心 K/D/A 与浅绿 / 浅红近期条，统一留白、圆角、文字和选中层级。

**三个核心使用场景**

| 场景 | 用户最需要回答的问题 | 首屏重点 |
| --- | --- | --- |
| 选人中 | 阵容缺什么？我的英雄适合吗？有没有更合适的候选？ | 己方阵容、已公开敌方、本人英雄调整、最多三个主要建议 |
| 对局前 / 对局中查看 | 双方近期状态如何？谁熟悉当前英雄？ | 十人阵容、明确标注的段位、同模式近期胜负与 K/D/A；当前英雄熟练度放展开区 |
| 赛后 | 我这局表现如何？哪些指标偏弱？ | 胜负和 K/D/A、关键贡献、同场比较、必要时展开图表 |

**优化清单与优先级**

| 优先级 | 当前观察 | 建议与用户收益 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 当前近期汇总排除自定义和短局，但仍混合不同模式 | 默认分析当前模式；“全部模式”作为显式选项。普通与海克斯大乱斗分别统计，卡片写清模式 | 当前模式的胜率、场均 K/D/A、常用英雄和近期条采用同一口径；不足样本显示实际场数 |
| P0 | 用户已反馈滚动、切页和鼠标移动卡顿；列表已开始做可见区域绘制 | 把流畅度作为发布条件，覆盖十人数据加载、英雄库、长战绩、悬停和缩放 | 建议目标：60 Hz 下绘制耗时 p95 < 8 ms，长列表无明显停顿；另测高刷新率。持续重绘诊断与真实交互分别记录 |
| P0 | 已有真实 / 历史标签和请求关联，但连接状态缺少账号、大区及数据新鲜度概览 | 增加一处简洁状态区：当前账号、大区、游戏阶段、最近更新时间；切账号时清理旧账号视图 | 用户能明确判断“这是谁、哪一局、什么时候的数据”；旧回复不能覆盖新账号或新局 |
| P0 | 刷新阵容会先清空玩家资料；完成提示主要在底栏，单人失败缺少就近操作 | 同一局刷新保留上一份结果并标注“更新中”；逐人更新，失败卡片可重试；新局先清空旧局 | 一人失败不阻塞其他九人；查询失败、无历史、身份未公开、样本不足有各自状态 |
| P1 | 选人助手和对战助手分开；进入选人会自动切页，点击玩家会离开当前阵容 | 合并为“对局助手”，按阶段展示选人 / 双方分析。玩家详情用侧边抽屉，深度查询保留独立入口 | 选人和双方战绩可在同一工作区切换；关掉玩家详情后原阵容、选择和滚动位置仍在 |
| P1 | 卡片展示近期常用英雄，但不能直接回答“他会不会当前这个英雄” | 玩家展开区增加当前英雄在本次样本中的场次、胜率、K/D/A；无记录时明确说明 | 小样本显示场数；“未在这批记录中出现”不被写成“不会玩”；不声称生涯熟练度 |
| P1 | 大乱斗推荐目前主要按坦克标签和胜率排序，解释偏笼统 | 分开呈现英雄强度、阵容补位、近期熟悉程度；先给三个候选，每个附一两条可核对的理由 | 不把坦克统一视为最佳选择；只推荐当前可选英雄；排位对位统计不被称为对线期胜率 |
| P1 | Buff/Debuff 卡片目前只直接显示第一项，其余需要进入详情 | 优先展示与当前英雄相关的主要增强和削弱；完整列表展开查看，标明模式及版本 | “承受伤害 +5%”显示为削弱；缺失调整不会显示成无调整；普通与海克斯数据不混用 |
| P1 | 自动选禁同时存在“本地编辑、已应用规则、运行开关”，操作结果不够直观 | 明确显示“未保存修改 / 已应用 / 运行中”；在数据充分时显示当前候选、等待条件及跳过原因 | 用户能知道当前应用的规则和下一步动作；保存不自动启用，设置页的停止入口清晰可见 |
| P2 | 场数与来源覆盖已落实；LCU 仍受客户端上限限制，SGP 已实测取得 200 场 | 后续可把默认分析深度集中到设置，页面保留快捷切换和实际数量 | 请求、取得和有效场数分别表达，不放大接口实际返回的样本 |
| P2 | 战绩详情已有贡献条和雷达图，但比较口径需要持续保持清楚 | 默认展示关键数值和贡献条，雷达留在详情；同模式、同位置比较等有可靠样本后再加 | 己方占比、全场排名、雷达归一化分别标注；输出占比 32% 仍可在最高伤害轴到外圈 |

**建议的页面结构**

| 导航 | 页面职责 | 迁移方式 |
| --- | --- | --- |
| 对局助手 | 当前选人、双方近期数据、英雄详情、推荐 | 合并现有选人助手和对战助手，顶部用简短阶段切换 |
| 战绩 | 我的战绩、玩家搜索、单局详情 | 战绩分析和查询采用相同的详情结构，明确当前查看对象 |
| 自动选禁 | 选 / 禁优先级、运行状态、执行结果 | 保留独立入口；对局页只显示运行摘要与停止按钮 |
| 设置 | 分析深度、默认统计口径、主题、窗口行为 | 公共数据刷新和连接诊断等低频操作集中管理 |

“进入选人时自动切到对局助手”建议做成偏好。默认自动连接，但用户已经在查看某位玩家或复盘时，应提示新对局并提供进入按钮，避免后台更新打断阅读。

**十人卡片的信息层级**

保留已经确认的双列五行和浅绿 / 浅红胜负，不继续把信息堆进每张卡。

1. 第一层：当前英雄头像、召唤师、明确类型的段位、场均击杀 / 死亡 / 助攻。
2. 第二层：最近十场胜负与逐场 K/D/A，左新右旧。文字保留，不仅用颜色区分。
3. 第三层：这批记录的统计模式、有效样本、胜率和常用英雄；详细解释收进悬停或展开区。
4. 展开区：当前英雄样本、完整战绩、最近使用位置、数据来源与时间。

建议先校正昵称、核心 K/D/A、辅助说明的字号和对比度。默认 1280 × 860 下仍需完整看到十人；缩小窗口时优先压缩说明区和空白，避免继续缩小核心数字。

**图表使用原则**

- 单局比较优先使用可排序的水平条形图，直接显示原始数值、己方占比和全场名次。
- 雷达图用于展开比较，显示各轴基准；不从输出、承伤等原始数值推导没有依据的“综合能力”。
- 趋势应在相同模式内计算。辅助与输出英雄的伤害不能直接用同一阈值评优劣。
- 阵容分析使用前排、开团、控制、持续输出等可解释标签。仅凭五个英雄生成精确的“阵容胜率”或伤害百分比分配，依据不足。
- 当前十人首屏不建议增加十张雷达图、多个环形图或综合评分。这些会降低扫读速度，也会增加绘制成本。

**建议推进顺序**

第一轮完成数据口径、状态反馈和流畅度：同模式统计、账号 / 大区标识、局次切换、逐人刷新及错误重试。先建立“显示正确且用着顺”的基础。

第二轮调整工作区：合并对局页面、增加玩家详情抽屉、保存查看位置，简化顶栏，并把低频设置移出首屏。

第三轮完善决策信息：当前英雄样本、可解释的阵容建议、Buff/Debuff 摘要、自动选禁的执行预期。赛后趋势和更细的对比排在这些之后。

建议现阶段继续使用普通原生窗口。悬浮窗、游戏内覆盖层、皮肤和更多图表可以等核心流程稳定后再评估。

**下一轮建议范围**

数据口径、状态和逐人刷新已经实现。后续优先评估页面合并与玩家详情抽屉，并完成实际鼠标、滚动和切页的输入验收；阵容推荐解释和禁选执行预期继续保留为产品规划。
